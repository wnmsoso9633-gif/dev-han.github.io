01

정적·동적 두 모드를 하나의 쿼리로 운영하기

Problem

저장값 기준(정적)과 재계산값 기준(동적)을 모두 제공해야 해서, 모드별로 쿼리를 복제하면 변경 때마다 두 곳을 고쳐야 했습니다.

Approach

세션의 계산 모드를 기준으로 SQL의 테이블명을 실행 직전에 치환했습니다. 정적은 기본 테이블, 동적은 동적 전용 테이블 세트를 가리키며, 동적 조회가 실패하면 정적 값으로 안전하게 대체합니다.

Outcome

쿼리는 한 벌만 관리하고 모드 전환은 치환 규칙에서만 처리합니다. 새 화면을 추가해도 같은 규칙을 그대로 재사용합니다.

02

키가 서로 다른 두 테이블 동기화하기

Problem

원본과 동적 테이블이 각자 MAX+1로 순번을 채번해, 같은 제품이어도 PK가 달라 키 매칭이 전혀 되지 않았습니다.

Approach

복잡한 키 재지정 대신 PK 기준 매칭 + 비어 있는 값만 채우기라는 단순한 규칙으로 정했습니다. 반드시 덮어써야 하는 값만 예외 컬럼 배열로 분리해, 필요할 때 추가할 수 있게 했습니다.

Outcome

샘플 데이터로 실제 키 값을 대조해 원인을 확정했고, 보정 로직을 늘리는 대신 규칙을 단순하게 유지해 운영 안정성을 높였습니다.

03

대규모 재계산의 격리와 범위 일치

Problem

전체 프로젝트의 동적 결과는 프로젝트 × 단위공정만큼 재계산해야 의미가 있는데, 브라우저에서 반복 호출하면 화면이 멈추고 중간 실패를 다루기 어려웠습니다.

Approach

서버 액션 하나가 대상 단위공정을 순회하며 기존 재저장 메서드를 호출합니다. 각 호출이 자기 트랜잭션을 가지므로 하나가 롤백돼도 나머지는 계속 진행하고, 성공·건너뜀 건수를 집계해 안내합니다.

Outcome

대상 연도·기간에 맞지 않는 프로젝트는 재계산과 조회에서 함께 제외해, 화면에 보이는 숫자와 실제 계산 범위를 일치시켰습니다.
